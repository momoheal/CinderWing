# M3 讲解：小龙怎么"带你去"需要你处理的任务？

> 版本：v0.10.0（M3）　｜　对应代码：`app/activator.py`、`app/bubble.py`、`app/task_source.py`、`app/pet_window.py`
> 阅读对象：零基础的你。看完你能讲清楚：**点一下小龙的气泡，豆包工作为什么能直接跳到对应会话。**

---

## 一、M3 要解决什么问题

M2 做完后，小龙已经能播报真实任务：开始、进度、完成。但"需要你决策"
时还有个断档——小龙在屏幕角落喊"需要你确认"，你还得自己去任务栏找
豆包工作、自己翻到那个会话。

Codex Pets 的体验是：**点宠物 → 直接跳到出事的地方**。M3 就做这件事：

1. 小龙弹出红色"需要你决策"气泡时，**点气泡**直接打开豆包工作，
   并切到那个任务所在的会话；
2. 多个任务同时跑时，点气泡展开**多任务面板**，**点哪一行就跳哪个会话**；
3. 鼠标移到可点击的位置会变成**手型光标**，并给出文字提示；
4. 顺带把"需要决策"的识别做得更准（见第四节，新发现的 10082 块）。

## 二、白话原理：什么是"深度链接"（Deep Link）

网页链接你很熟：`https://...` 开头，浏览器看到就打开网页。
桌面软件也可以注册自己的"链接"，叫**自定义协议**。比如：

- `mailto:xxx@xx.com` → 系统自动打开邮件软件；
- `weixin://...` → 打开微信。

豆包工作安装时也在 Windows 注册了自己的协议。我们要做的，就是找到
"打开某个会话"的链接长什么样，然后让小龙替你"点"这个链接。

### 我们是怎么找到这个链接的（逆向三步）

**第一步：查注册表，确认协议名和启动命令。**

Windows 把"某个协议由哪个程序打开"记在注册表里。查
`HKEY_CURRENT_USER\Software\Classes` 发现豆包工作注册了
`doubaowork` 协议，打开命令是：

```
DoubaoWork.exe -- --open-url="%1"
```

意思是：任何 `doubaowork://...` 链接，系统都会交给 DoubaoWork.exe
处理。

**第二步：翻前端代码，找"会话页"的地址格式。**

豆包工作的界面是网页做的（Electron 应用 = 浏览器壳 + 网页）。
它的网页代码明文放在安装目录 `app\local_webcontents` 下。
用关键词扫描（扫描脚本保留在 `tools/_m3_scan_routes.py`、
`_m3_scan_routes2.py`，可复跑）找到了路由拼接代码：

```js
"/chat/".concat(V.conversation_id)
```

也就是说，客户端内部"某个会话页"的地址是 `/chat/<会话id>`，
网页宿主名是 `doubaowork-chat`。

**第三步：拼出完整链接。**

组合起来，最终的激活链接是：

```
doubaowork://doubaowork-chat/chat/38446069288761602
```

`38446069288761602` 就是 M2 里从 IndexedDB 读出来的会话 id。
系统收到这个链接 → 启动/唤起豆包工作 → 它打开对应会话页。

> 还有一种"包装格式" `doubaowork://doubaoworkapp/open-url?url=...`
> 作为备用，记在 `app/activator.py` 注释里；如果将来直连格式失效
> 就换它。

### 兜底方案

万一协议没注册成功（比如绿色版客户端），小龙会退而求其次：
用 Windows API 按进程名 `DoubaoWork.exe` 找到主窗口，把它
恢复并抢到最前面（`bring_to_front`）。虽然不能直达会话，
至少保证豆包工作出现在你眼前。

## 三、代码导览：点击是怎么一级级传过去的

整条链路像接力：

```
你点气泡
  → Bubble.mousePressEvent     判断点的是哪里
  → jump_requested 信号         喊一嗓子"要去这个任务"
  → PetWindow.jump_to_task     播放点击音效
  → activator.activate_conversation   打开深度链接
  → Windows 系统 → 豆包工作 → 对应会话
```

### 1. `app/activator.py`（M3 新增，约 120 行）

- `activate_conversation(conversation_id)`：拼链接、发链接。
  - 先校验会话 id 必须是**纯数字**（真实 id 都是数字串），
    防止演示数据误打开错误页面；
  - 用 Qt 的 `QDesktopServices.openUrl()` 发出，它底层就是
    Windows 的 ShellExecute，和你在浏览器地址栏敲链接等效；
  - 失败则调 `bring_to_front()` 兜底。
- `bring_to_front()`：用 ctypes 调 Win32 API——`EnumWindows`
  遍历所有窗口，`QueryFullProcessImageNameW` 查每个窗口属于哪个
  exe，找到 DoubaoWork.exe 的有标题主窗口，`ShowWindow` 恢复、
  `SetForegroundWindow` 置前。

### 2. `app/bubble.py`：气泡学会了"分清你点的是哪"

M2 的气泡点哪里都只是展开/收起面板。M3 改成三级判断：

| 当前状态 | 你点的位置 | 行为 |
|---|---|---|
| 收起 + 红色"需要决策" | 气泡任意处 | **直接跳转**该任务会话 |
| 展开的多任务面板 | 某条任务行（且有会话 id） | **跳转该行**的会话 |
| 展开的多任务面板 | 空白处 | 收起面板 |
| 收起 + 普通状态 | 气泡 | 展开多任务面板 |

实现要点（以后你自己改时找得到）：

- 每个任务多了两个字段：`conv_id`（会话 id）、`section_id`；
  只有 `conv_id` 是数字串时任务才算 `jumpable`（可跳转）。
- 面板每行的矩形在 `paintEvent` 里画的时候顺手存进
  `self._row_rects`（字典：任务 key → QRect），点击时拿
  鼠标坐标去查落在哪个矩形里——这就是"热区"的常见做法。
- `mouseMoveEvent` 里判断鼠标是否在手型热区上，是就
  `setCursor(PointingHandCursor)`（手型光标）。
- 新增信号 `jump_requested = Signal(str)`，参数是任务 key。
  Qt 里"界面组件不直接干活，只发信号，外面接信号的人去干"
  是标准解耦写法，这样气泡不需要知道豆包工作的存在。
- 红色决策气泡底部提示文案改为
  **"点击打开豆包，去处理决策 →"**；
  面板右上角提示 **"点任务打开 · 空白收起"**。

### 3. `app/task_source.py`：把会话 id 一路带出来

M2 已经从 IndexedDB 读出了会话 id（`_conv_ids`），但只存在
内部状态里没往外发。M3 把它加进了所有事件回调的参数：

```python
on_event(kind, body, key, name, progress, conv_id, section_id)
on_progress(key, percent, body, conv_id, section_id)
```

开始、进度、等待、完成——每个节点的气泡都知道自己属于哪个会话，
点下去才知道该跳哪。

### 4. `app/pet_window.py`：接信号的人

新增 `jump_to_task(key)`：从气泡里查出任务 → 播"click"音效 →
调激活器。没有会话 id 时只记日志、不乱抢前台。

## 四、意外收获：发现了真正的"需要决策"信号（10082 块）

M2 时我们一直没抓到真实的"等待用户决策"样本，只留了个
`permission_interact` 钩子（实测恒为 `<Undefined>`）。

M3 真机测试当天，`pet.log` 里冒出一行：

```
[task_source] unknown block_type=10082 content_keys=['interaction_ask_block']
```

这正是 M2 就埋好的"未知块类型上报"钩子在干活。dump 它的内容后
确认：**10082 = 交互提问块**，就是 Agent 用结构化卡片向你提问
（`interaction.ask`）时产生的块，里面有问题 id、标题、选项、
回答状态。这就是"需要你拍板"最标准的信号。

判定规则（`app/task_source.py`）：

- 块内 `interaction_ask_block.status == 1` → 待回答 → **WAITING**；
- `status == 2` → 已关闭（已回答或超时，实测超时样本的文案是
  "未提供回答"）→ 不打扰你。

同时 10082 加入了已知块类型表，每次见到新的 status 取值都会
写进 pet.log，方便以后继续校准。

> 诚实说明：目前真机上只采到 status=2（超时关闭）这一种样本，
> status=1（待回答）是按状态枚举惯例做的判定。等下次 Agent 真的
> 弹出问题卡片、小龙及时冒出红色气泡，这条规则就算闭环验证。
> 在此之前请看一眼 pet.log 里 `interaction_ask_block status=` 的记录。

## 五、演示模式：安全地"假装跳转"

`--sim` 演示模式（`app/dev_sim.py`）里两个假任务也配了假会话 id，
这样面板行、手型光标、红色提示都能演示。但假 id 不能真的去打开
客户端（会跳到不存在的页面），所以：

- `app/activator.py` 有个开关 `SIMULATE`；
- `main.py` 发现 `--sim` 时把它置为 True；
- 此时点击只在 pet.log 写一行
  `activator: [SIM] would open doubaowork://...`，不真的跳转。

## 六、怎么自己验证 M3

### 1. 离屏自动化测试（5 项，已全部通过）

```bat
.venv\Scripts\python.exe tools\test_m3_jump.py
```

它用 Qt 的"虚拟屏幕"模式（不弹窗）验证：
红色决策气泡单击→发跳转信号；普通气泡单击→展开面板不跳；
面板里点第二行→跳第二个任务；无会话 id 的行不跳；
激活器对假 id 拒绝、对数字 id 在演示模式只记录。

### 2. 肉眼演示（模拟数据）

```bat
:: 双击 sim 启动，或命令行：
.venv\Scripts\pythonw.exe -m app.main --sim
```

- 第 9 秒：红色"需要你决策"气泡，底部有
  "点击打开豆包，去处理决策 →"；
- 点气泡（决策态）：不会展开面板，而是模拟跳转（看 pet.log）；
- 第 14 秒后恢复普通态，点气泡 → 多任务面板，
  鼠标移到任务行上变手型，点某行 → 模拟跳转对应会话。

本轮真机截图保存在 `tools/_m3_bubble_waiting.png`（红色决策气泡）
和 `tools/_m3_bubble_panel.png`（两行任务的面板）。

### 3. 真机验证（真实数据，需要你观察一次）

正常双击 `启动宠物.bat` 后：

1. 下次豆包工作里**同时有两个任务**在跑时，点小龙气泡，
   应展开两行任务的面板，每行带进度条；
2. **点任意一行**，豆包工作应跳到那个任务所在的会话
   （这一步我发过链接、进程侧正常，但最终画面效果需要你亲眼看一次；
   如果没跳，告诉我，我换备用的包装格式链接）；
3. 下次 Agent **弹问题卡片问你**时，小龙应在 3 秒内冒红色
   决策气泡；如果没冒，把 `assets\pet.log` 里
   `interaction_ask_block status=` 那行发我。
