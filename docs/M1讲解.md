## 二、核心概念（白话版）

### 1. 序列帧动画 = 高速翻页

电影其实是一张张静止照片快速播放。我们的动画同理：`assets/frames/idle/`
里有 `00.png … 07.png` 共 8 张透明图（程序合成的身体起伏呼吸），程序每隔
0.5 秒换一张，眼睛就觉得它在一起一伏地呼吸。

### 2. QTimer：程序的 "闹钟"

`QTimer` 可以 "每隔一段时间" 或 "等待一段时间后" 触发一次。本项目有这些用法：

* **动画帧定时器**（`SpritePlayer` 内部）：每隔 1/FPS 秒换下一张图；
* **眨眼 / 挠痒定时器**（`PetWindow`）：随机间隔，到点才做一次小动作；
* **自动入睡定时器**：安静满 2 分钟触发一次；
* **晕倒回站姿定时器**：松手/失败晕倒后，等 0.8–1.4 秒回站姿。

"随机等待" 让动作没有机械的规律感，但触发的**内容**仍然是确定的。

### 3. 信号与槽：Qt 的 "传话机制"

Qt 里对象之间不直接喊，而是 "发信号"，事先 "连好" 的函数会自动执行。本项目的链路：

```
帧定时器超时
   → SpritePlayer 换帧、发出 frame_changed 信号
      → PetWindow 收到新图，update() 重画
动作最后一帧播完
   → SpritePlayer 发出 finished 信号
      → PetWindow 回到静止站姿（_enter_rest）
气泡事件类型变化
   → Bubble 发出 state_changed(kind) 信号
      → PetWindow 按事件类型选动作（说话 / 庆祝 / 晕倒 / 回站姿）
（纯进度百分比更新不发信号，避免数字一跳宠物就重新演一遍）
```

最后一条是本次重构的核心：**动作不再由演示脚本直接指定，而是统一由
"气泡状态" 驱动** —— 以后 M2 接上真实任务，宠物反应自动就对了。

### 4. 待机节奏：以静为主，呼吸做在身体上

为了 "安静、不抢注意力"，待机**不是**一直做大幅度动作，也不是完全僵住：

```
idle 8 帧循环（2fps，4 秒一圈）：
   肩胸随呼吸轻轻上抬（峰值约 3px）、红色腹甲向外微微鼓起、
   头部只做约 1px 的极轻微协同，双脚完全锚定不动（实测脚部
   像素零变化）——这 8 帧不是画出来的，是程序以睁眼站姿帧为底、
   按 Live2D CubismBreath 的思路做局部位移形变合成的
   （build_frames.py 的 body_breath，余弦曲线保证首尾无缝）
   → 每随机 1.8–4.2 秒插播一次专用 blink（5 帧，只动眼睑，
      头和身体像素零变化，约 0.5 秒）
   → 每随机 30–70 秒偶尔挠一次痒痒（4 帧）
   → 连续 2 分钟无任何动静：自动入睡
```

为什么呼吸不用"整体放大缩小"或"整体上下平移"？你之前明确否掉过：
整体缩放像气球，整体上下晃像蹦跳，都不像呼吸。v0.8 查证了业界做法
（Live2D 官方 CubismBreath、anysoul 的 idle base 层）：呼吸是把一条
正弦波同时叠加到**胸腔/身体起伏、肩头、头部极轻微协同**上，而不是
头冻结+只有肚子横鼓。所以现在的形变分三层：肩部垂直上抬（越靠近脚
衰减到 0）、腹部高斯外鼓（脚下淡出）、胸腔额外上抬，头部只分到约
一半幅度。实测峰值帧头部质心上移约 1px、胸部约 1px、脚部 0 变化。

> **踩坑记录（位移方向）**：图像形变里"让内容上移 N 像素"，采样时
> 要从源图的 `y + N` 处取像素（输出位置 y 显示源位置 y+N 的内容，
> 内容才会往上走）。第一版写反成 `y - N`，结果龙在"吸气"时整体
> 下沉 1px，是用分区质心测量（头/胸/腹/脚四段分别算质心 y）才发现
> 的。教训：**形变对不对，不要靠肉眼猜，用质心/差分图量化验证。**

熟睡时画面停在蜷缩帧（tap3 最后一帧冻结），`paintEvent` 再给它
2 像素、2.8 周期的极轻微整体起伏，表现"睡着了还在喘气"。

如果定时器到点时你正在点它 / 拖它 / 气泡在显示，这次微动会被跳过、
重新计时（代码里的 `_quiet()` 检查）。

> **踩坑记录 1**：`_quiet()` 判定"没在播放动画"靠的是
> `player.name is None`。而静态站姿用的 `show_frame("idle", 0)` 早期
> 也会把 `name` 设成 `"idle"`，导致待机时程序一直以为"动画在播放"——
> 呼吸、眨眼、挠痒、自动入睡**全部静默失效**。修复方法：静态显示某帧
> 时把 `name` 置回 `None`（见 `sprite_anim.py` 的 `show_frame`）。
> 教训：**"显示一帧"和"播放一段动画"是两种状态，不能共用同一个标记。**
>
> **踩坑记录 2**：点击反应（咆哮/扑咬）播完后，早期只回呼吸循环、
> 没有重新武装自动入睡定时器，结果点过一次之后小龙再也不会自动睡觉。
> 现在 `_on_anim_finished` 区分动作来源：自发的眨眼/挠痒只回呼吸
> （不重置入睡计时），点击/庆祝等"你主动互动"的动作走完整
> `_enter_rest()`，入睡定时器重新计时。

### 5. 点击、长按还是拖拽？按下之后观察

按下鼠标时记录起点和位置，然后：

* 移动超过 6 像素 → 判定为**拖拽**：播被抓起动画、窗口跟着鼠标走；
* 按住不动超过 0.6 秒 → 判定为**长按**：播打哈欠→蜷缩，然后**保持熟睡**
  （最后一帧冻结、身体持续缓慢起伏），直到你下次点击/拖拽才唤醒；
* 松手时两者都没发生 → 判定为**点击**，再看点击的 y 坐标分区：
  * 落在窗口上部 42% 以内（头 / 角）→ tap1 咆哮喷火；
  * 落在中下部（身体）→ tap2 扑咬。

这套 "按下→观察→松手才定性" 的思路，是处理鼠标交互的通用套路。

两个实现细节：

* **帧冻结（hold_last）**：播放器播完一遍后默认发 finished 回站姿；
  睡觉改为 "停在最后一帧、不发 finished"，画面一直保持熟睡，
  配合垂直平移就是 "熟睡起伏"。
* **拖拽慢晃**：drag 动画只循环前 5 帧（被拎住左右慢晃，**2fps**），
  松手才显示第 6 帧螺旋眼晕倒，晕倒停留 0.8 秒后由定时器调
  `_enter_rest()` **必定回站姿**（早期版本松手后会一直重复被拉动作，
  就是因为少了这个回站姿定时器）；回站姿定时器用的是**有父对象的
  QTimer**（早期无父对象的 `QTimer.singleShot` 实测不生效）。

### 6. 美术从哪来：青蓝底设计稿 + AI 抠像 + 程序合成

所有素材**一律不用绿色背景**，统一用青蓝幕布 (0,170,200)，角色始终是
你最喜欢的**最早那版可爱小龙**（大脸、雀斑、金属角箍），所有条图都以
核心形象图/标杆帧为锚点用图生图延展，防止长相漂移：

```
blink 睁眼站姿帧（青蓝条图第 0 帧） → idle 呼吸合成的唯一起点 + blink 睁眼帧
blink_closed 闭眼单帧（青蓝，双翅完好）→ 与睁眼帧做眼部软边混合 → blink 5 帧
程序合成（不重新画图）              → idle 8 帧（body_breath 身体起伏）
scratch 青蓝条图（挠痒 4 帧）       → scratch 4 帧
talk 青蓝条图（说话 6 帧）          → talk 6 帧
喷火条图 A/B/C（v0.8 重生，各 3/3/2 格）→ tap1 8 帧（蓄力→初火→猛喷→
                                          水平火柱→余烟→得意，火只从嘴出）
扑咬条图 + 专用扑击帧               → tap2 5 帧
睡眠条图（青蓝，无鼻涕泡）          → tap3 7 帧
drag_a + drag_b（青蓝）             → drag 6 帧（慢晃 5 + 晕倒 1）
开心条图（v0.8 重生，3 格展翅欢呼） → happy 3 帧
```

条图切片、抠像、缩放、呼吸/眨眼合成都在 `tools/build_frames.py`
（v0.8 起旧的 `prep_drafts.py` 拼装流程不再被依赖）。

### 7. 抠像：为什么手写色度键治不好，最终换成 AI 语义分割

v0.6–v0.7 用绿色/青蓝幕布 + 手写色度键抠像，多轮返修始终无法根治
**身体、脸、腿、翅膀内部被抠出透明/白色色块**。v0.8 查证资料后定位到
真正的根因——**溢色（spill）**：影棚灯光照在幕布上，幕布的彩色光
反射到角色迎光侧的鳞片上，把深色鳞片染成了幕布色相。这时逐像素规则
面对的是"被幕布色光照亮的龙鳞"和"幕布本身"颜色几乎相同的局面：
阈值收紧→龙鳞被抠穿成洞，放松→幕布残色删不干净。这是色度键的原理性
缺陷，调参数永远在两个故障之间摇摆。业界（影视抠像、游戏精灵处理）
的主流解法是 **AI 语义分割**：让模型判断"每个像素属不属于主体"，
颜色像不像背景根本不参与决策。

v0.8 方案（`tools/build_frames.py`，模型用 rembg 自带的 U²-Net，
模型文件 176MB 已随项目放在 `tools/.u2net/`，离线可跑）：

```
① rembg remove(post_process_mask=True)：AI 输出主体遮罩，
   金属角箍、獠牙、眼神光、腹甲高光、翼膜骨架这些"亮但属于龙"的
   细节全部保留，不再可能被当背景删掉；
② 组件清理（连通域分析）：只保留最大组件（身体 + 与身体相连的
   翅膀/尾巴/火焰），以及面积够大但不触边的内部小组件（火星）；
   一切触边框的碎块删除——顺带解决喷火条图火焰越界串到邻格；
③ 顶部吊线开口：被拎起条图里模型画的细"吊线"是触顶的窄竖条，
   对顶部 30% 条带做水平形态学开运算（K=7），细线消失、头和翅膀
   这种宽结构不受影响；
④ 封闭青口袋清除：AI 后处理偶尔会把"翅膀+尾巴+身体围成的封闭
   幕布区"填成不透明；对不触边、颜色是高饱和青蓝的封闭组件清零
   （翼膜间开口通向画面外的真实空隙本来就是透明的，不受影响）；
⑤ 统一 place()：按 p80 高度/中位宽度缩放、脚底锚定（FEET_Y=238），
   宽帧夹紧保证翅膀全在画幅内；
⑥ 画布级 final_clean() 再清一遍小碎片；边缘抗锯齿用颜色外扩
   （硬内芯 + 1px 半透明环），不用模糊羽化。
```

为什么不用更强的 ISNet / BiRefNet？U²-Net 在我们的素材上轮廓已经
干净、细节保留充分，且模型成熟稳定；后续某套图边缘发软时可以单帧
换 `isnet-general-use` 对比，这是一行模型名的改动。

经验总结：**"这个像素什么颜色"是低级线索，"这块区域语义上是不是
主体"才是可靠线索**；手写色度键适合主体颜色与背景差异极大且光照
可控的场景，AI 分割适合我们这种带反光、半透明翼膜、火焰特效的角色。

### 8. 质检：必须用彩色底

帧检查拼图（`*_cut_check.png`）统一铺**饱和品红底色 (200,30,160)**：
白色/浅色高光（獠牙、眼神光、火焰尖）在白底上会被 "藏" 起来，在强
彩色底上一眼就能发现。禁止再用白底或深灰底检查。

### 9. 音效：QSoundEffect

`assets/sfx/` 里的 WAV 由 `tools/make_sounds.py` 纯代码合成（没有用
任何网上的音效文件，避免版权问题）。托盘菜单勾选 / 取消 "音效开关"，
只是把 `Sfx.enabled` 置为 True/False。

### 10. 位置记忆：读写 JSON

JSON 是一种最简单的文本数据格式。`assets/config.json` 内容长这样：

```
{"pos": [-464, 1085]}
```

拖拽松手时把当前窗口坐标写进去；启动时能读到就用，读不到（第一次
运行）就放到屏幕右下角。

## 三、任务事件气泡 + 动作（对标 Codex Pets）

小龙在任务的 **开始、重要进度、需要你决策、结束（成功/失败）** 各
节点都用**明确的文字气泡**说出来，并且配特殊动作：

| 事件 | 气泡标题（颜色 / 停留） | 宠物动作 |
| ---- | ---- | ---- |
| START 开始 | 任务开始（橙，12s 无更新才隐藏） | talk 说话（气泡可见期间循环） |
| PROGRESS 进度 | 任务进度（黄，12s） | talk 说话 |
| WAITING 决策 | 需要你决策（红，**20s**） | talk 说话（专注地提醒你） |
| DONE 完成 | 任务完成（绿，8s 后自动消失） | happy 开心庆祝 |
| FAIL 失败 | 任务失败（红，8s） | 螺旋眼晕倒一下 |

### 气泡里有什么（v0.6 重写）

* **任务名 + 状态标题**：头部左侧是彩色状态标题，右侧是任务名，
  多条通知不会再分不清在说哪个任务；
* **状态正文**：比如"正在识别重复文件…"、"需要你确认：是否删除
  12 个重复素材？"，过长自动换行；
* **实时进度条 + 百分比**：任务进行中，进度数字由 `update_progress()`
  每秒推动，进度条平滑增长；**纯进度刷新只重绘气泡，不打断宠物动作**；
* **多任务面板**：同时存在多个任务时，气泡底部提示"点击查看全部任务"，
  点击后展开"任务进度（N）"面板，逐任务列出名称、状态、进度条和
  百分比，展开期间不自动隐藏；再点一次收起；
* **融合尾巴**：气泡尾巴和圆角框体是**同一条连续轮廓**（一条
  QPainterPath 画到底），填充和描边同路径完成，不会出现"单独贴了个
  三角"的接缝；空间不够时尾巴自动翻到气泡顶部。

### 任务模型（给以后接真实数据用）

v0.6 不再是"通知排队"，而是维护一个**任务表**（`bubble.tasks`，按任务
key 索引）：

```
notify(kind, body, key, name, progress)   # 状态节点：新建/更新一个任务
update_progress(key, percent, body)       # 实时进度：静默刷新，不触发动作
```

* 同一个 key 的事件**立即更新**，只有事件类型真的变化（如
  PROGRESS→WAITING）才发 `state_changed` 信号让宠物换动作；
* 焦点任务（气泡主体）按紧急度选取：**需要决策 > 刚完成/失败 >
  最近更新的运行任务**，所以 B 任务在跑时 A 弹出决策，焦点会立刻
  让给 A；
* 完成/失败提示 8 秒后由一个 0.5 秒的清扫定时器移除；运行中的任务
  12 秒没有新进度则气泡先隐藏（任务保留），新进度到达立刻再弹出。

M2 接上豆包工作真实任务后，key 就是任务 UUID，这套模型直接可用；
M3 会让点击气泡（尤其 WAITING 时）直接打开豆包工作里对应的会话。

**现在就能试**（托盘右键小龙图标）：

1. "模拟：任务全流程"—— v0.6 起演示**两个任务并发**（约 25 秒）：
   两个任务先后开始、进度条实时增长、A 中途请求决策、随后继续并完成、
   B 最后完成；期间点击气泡可看多任务面板；
2. "测试：完成通知"—— 只弹一条完成气泡；
3. 鼠标**中键**点小龙也会弹一条完成气泡（隐藏测试入口）。

## 五、小作业（建议动手，改坏了用 git 或问我）
